# Windows Shell icon extraction contract

## Scope and interaction

`src/interop/icon_windows.c` is the read-only Windows acquisition boundary for a Shell item's icon. It consumes an already-owned/initialized COM `IShellItem *` and an optional bounded path used only for the historical system image-list fallback. It does not enumerate catalog entries, identify app keys, hash or install files, create desktop entries, watch catalog sources, launch applications, or initialize COM. The separately specified portable PNG encoder is in `png_writer_contract.md`.

The caller receives one caller-allocator-owned, top-down, straight-alpha RGBA8 image. It may encode those bytes with the separate PNG writer. Extraction is synchronous and uses local state only. Caller serializes the item, allocator, and output record; no handles or pointers are retained after success.

## Records, lifetime, and public interface

`icon_windows_allocator_t` contains a borrowed context and a complete allocate/deallocate callback pair. The pair must remain valid until `icon_windows_image_deinit`. A successful `icon_windows_image_t` stores the exact `rgba`, stride, dimensions, allocation size, and allocator pair needed to free once. The output image and required cleanup record must be naturally aligned, zero/empty, and disjoint from each other and inputs before the call. Ordinary failure leaves both records unchanged.

`icon_windows_extract_rgba(item, fallback_path, dimension, allocator, image_out, cleanup_out)` accepts sizes 16, 24, 32, 48, 64, 128, or 256. The optional path must be readable through a NUL terminator within 32,767 UTF-16 code units. Pointer-range arithmetic is validated for the full bound before scanning; the actual NUL-terminated extent must not overlap the output records or the checked first interface-pointer-sized range. The opaque COM object and allocator context must remain valid and disjoint for their lifetime; their full extents cannot be inferred or checked. Pointer ranges, overlap, alignment, allocator callbacks, and output emptiness are validated before native work. On success one allocation is transferred to `image_out`. `icon_windows_image_deinit` releases exactly that allocation and zeros the record; an empty record is accepted, while an incomplete nonempty record is preserved.

The cleanup record is zero on success and ordinary failure. If a `DeleteObject`, `DestroyIcon`, or `DeleteDC` operation fails, `CleanupRequired` transfers every unresolved exact handle identity, operation status/error, and last native error to the caller. `icon_windows_cleanup_retry` retries only those recorded handles, zeros each entry only after a successful close, and retains unresolved identities for another call. The caller must not discard a nonempty cleanup record.

All public symbols, fields, constants, statuses, ownership and thread rules are documented in `icon_windows.h`. On non-Windows systems extraction and native cleanup retry return `UnsupportedPlatform`; image deinitialization can still release a caller-owned image record.

## Native sequence

1. Validate all caller records, pointer arithmetic, overlap, alignment, allocator callbacks, supported dimension, and optional path bound. Compute the exact output allocation size without overflow.
2. Query `IShellItemImageFactory`, then request the square dimension with `SIIGBF_ICONONLY | SIIGBF_BIGGERSIZEOK`. A successful primary Shell bitmap is authoritative and is never replaced with fallback output.
3. If primary acquisition fails, use fallback only when the caller supplied a nonempty path and requested 16, 32, or 48 pixels. Call `SHGetFileInfoW` with `SHGFI_SYSICONINDEX`, get the corresponding small/large system `IImageList`, and call `IImageList::GetIcon` with transparent drawing. Other sizes do not use fallback.
4. For a primary bitmap, `GetObjectW` must report positive dimensions no greater than 512 by 512. `GetDIBits` converts that bitmap into a top-down 32-bit DIB, so ordinary device-dependent Shell bitmaps are accepted as well as DIB sections. The requested negative DIB height determines row orientation; `GetObjectW` may normalize the returned header height to positive, so validation checks its magnitude and the fixture verifies asymmetric first and last rows. Preserve alpha only when the source is an explicitly described 32-bit `BI_RGB` DIB section; other bitmap formats have no alpha contract and are treated as opaque. For fallback, draw the returned HICON into a requested-size top-down DIB with `DrawIconEx`, then read its actual `ICONINFO` mask.
5. Fallback mask alpha is synthesized only from that real AND mask. For color icons the mask has one image; for monochrome icons the first half of the double-height mask is the AND plane. A white mask bit is transparent and becomes alpha zero with zero RGB; a black bit is opaque. A monochrome AND/XOR invert operation (both bits set) has no faithful RGBA representation and returns a native failure rather than claiming transparency or opacity. When fallback pixels carry any alpha, preserve alpha values and only force mask-transparent pixels to alpha zero. A mask with no alpha information is the fallback source for opaque/transparent classification. Primary Shell bitmap alpha is never guessed from a mask or from its color bytes.
6. Sample the actual source into requested output dimensions with deterministic nearest-neighbor mapping: source coordinate `floor(output_coordinate * source_dimension / requested_dimension)`. Convert premultiplied Windows BGRA to byte-ordered straight-alpha RGBA. Alpha zero yields zero RGB. Otherwise each straight color is `min(255, (premultiplied * 255 + alpha / 2) / alpha)` using integer arithmetic.
7. Release temporary DCs, bitmaps, icons, and COM references. Transfer the output pixels only after native work and cleanup succeed. If cleanup fails, release the RGBA allocation and transfer all unresolved GDI handles in the cleanup record instead of publishing an image.

The API requires an initialized COM apartment compatible with the item. Shell and GDI calls are synchronous; this boundary does not retry an unresponsive Shell operation or start threads. The relevant Microsoft references are [`IShellItemImageFactory::GetImage`](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishellitemimagefactory-getimage), [`GetIconInfo`](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-geticoninfo), and [`ICONINFO`](https://learn.microsoft.com/windows/win32/api/winuser/ns-winuser-iconinfo).

## Errors, concurrency, and verification

Invalid arguments, unsupported dimension, out-of-memory, native Shell/GDI failure, unsupported platform, and cleanup-required ownership are distinct outcomes. No partial image is published. The Shell item remains borrowed; output storage and cleanup handles remain caller-owned according to the records. Calls are synchronous and have no shared mutable production state. The allocator and caller records must not be concurrently mutated.

The Windows fixture creates owned HICON/HBITMAP inputs, verifies asymmetric BGRA conversion, alpha-zero RGB clearing, opaque and clamped conversion, and exercises a monochrome double-height mask. It extracts a real stock Shell item through the primary API and uses real system image-list APIs for fallback after a failure seam. Native failure seams exercise Shell and image-list error handling and cleanup ownership. Windows production line and taken-arc coverage must each be at least 90% from execution on Windows; cross-compilation alone is not qualification. Linux unsupported-platform tests do not count as Windows native evidence.
