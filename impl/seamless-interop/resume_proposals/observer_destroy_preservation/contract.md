# O5 delivered-destroy preservation contract

## Chosen design

Keep the existing 512-key ordinary dirty FIFO for create/show/geometry/child hints. Add a separate fixed destroy mailbox for graph-tracked HWNDs and the one HWND currently being queried/offered. Destroy events for those protected keys bypass the ordinary FIFO, so child-hint overflow cannot erase them or claim continuity.

Add a read-only graph API, `interop_window_graph_list_tracked_windows`, that copies the unique HWNDs of every Active and Retiring entry into a caller array of `InteropMaxWindows` (64) elements and also returns the exact number of Free graph entry slots. It runs on the graph owner thread, has no callback/allocation, and leaves outputs unchanged on failure. Active+Retiring already share the 64-entry bound. Deduplicate equal HWNDs: old Retiring and new Active generations for the same numeric handle need one destroy key, because `note_destroyed` targets current Active/Deferred graph state and old generations remain governed by their own release proofs.

The observer owns a protected snapshot and the destroy mailbox. Bind the exact graph pointer and epoch before start; the observer keeps that binding for its lifetime. Add owner-thread `window_observer_sync_tracked(observer)` only for the one permitted external mutation, exact-proof `complete_retire`, which removes an entry and cannot admit or flush graph entries. Call it immediately after that operation and before another callback-capable call. Observer-owned mutations synchronize automatically. All admission-capable operations are observer-owned; see the normative binding amendment below.

## Capacity proof and backpressure

A fixed mailbox alone is insufficient: pending destroys can outlive their old graph entries while later offers flush Deferred children or admit new HWNDs. Capacity is therefore reserved before every callback-capable operation and every graph operation that may admit/flush records.

Use a 129-slot mailbox (`2 * InteropMaxWindows + 1`). Before a candidate query/offer or other callback-capable operation, take the callback-free graph snapshot and calculate:

`U = pending_mailbox_HWNDs ∪ current_tracked_HWNDs ∪ candidate_if_nonzero`.

For a graph mutation that can admit entries, reserve the conservative maximum post-mutation union:

`required = |U| + free_entry_slots_before_mutation`.

Reject double counting only when a key is known to already belong to `U`; otherwise keep the bound conservative. The primary candidate is already included in `U`; adding every currently Free graph slot bounds all newly Active entries, including the primary plus any Deferred descendants flushed by the offer. A single offer cannot activate more new entries than the exact pre-mutation Free-slot count because Active and Retiring entries share the fixed 64-entry array and retiring a generation does not free its slot. Thus the resulting mailbox plus post-mutation tracked set fits 129. For a callback-capable operation with no graph admission, `|U| <= 129` is sufficient.

If `required > 129`, perform bounded mailbox draining before the operation. If graph QueueFull prevents enough progress, return the existing observer `GraphQueueFull` status before any candidate query, callback-capable call, graph mutation, or new admission. Preserve every mailbox entry and old graph state; the coordinator drains graph events and retries. Do not clear entries to make space. Recompute the snapshot/free-slot bound after each successful drain because `note_destroyed` may retire graph entries.

The 129-slot bound covers one operation at a time. After a successful offer/flush, immediately call the callback-free snapshot and install its complete tracked set before any native/user callback. No Win32 callback can occur between the graph's internal mutation and this snapshot: graph mutation paths are pure except the application-key lookup, which occurs before commit and is covered by the candidate reservation. Arbitrary owner-message dispatch after the observer call is safe because before returning to it the union of pending keys and the newly tracked set must fit; if not, drain or return backpressure and keep message dispatch behind the caller's existing scheduling boundary. The proposal does not assume the platform can pause callbacks already being dispatched.

The graph snapshot includes exact Free-slot count so the admission reserve is meaningful. A stale or incomplete snapshot is never installed. Snapshot failure leaves the old set and all mailbox data unchanged and makes the observer fail closed. A post-mutation snapshot failure is an invariant violation; no external/native callback may run before the coordinator quarantines the owner and retains resources.

## Callback, drain, and graph-mutation order

1. `prepare_graph_mutation(observer, candidate_window, may_admit)` performs snapshot, capacity calculation, and bounded priority draining. It returns the existing `GraphQueueFull` status without changing graph/candidate state if the reserve cannot be established because the graph event ring blocks mailbox draining.
2. Before native enumeration reserve with candidate 0. Before each per-window native query/offer reserve with that HWND. This covers callbacks during enumeration/query and the app-key lookup inside an offer. An unknown not-yet-exported enumeration result is not falsely treated as tracked until it becomes the candidate.
3. `note_hint` keeps the existing owner-thread filter. Destroy for a tracked HWND or candidate merges into the mailbox, retaining the latest destroy stamp/event time. It makes no graph/native calls, allocations or waits. Non-destroy hints and untracked destroys use the ordinary FIFO.
4. Immediately after a graph mutation, synchronize the exact Active/Retiring snapshot before the next native call, callback dispatch or admission. This includes Active children admitted from Deferred flush and all Retiring cascade members.
5. Before later admissions, drain pending protected destroys first when needed for the capacity reserve. A successful `note_destroyed` result including accepted stale/unchanged disposition means that exact destroy was evaluated and can be consumed. QueueFull or an unexpected graph error consumes nothing; error paths fail closed.
6. When a normal dirty record becomes tracked and already carries a Destroy payload, promote that payload into the reserved mailbox before clearing the ordinary bits. If promotion cannot be reserved, keep both copies and return backpressure.
7. Ordinary FIFO overflow may request the existing full refresh; it never clears, overwrites or acknowledges the destroy mailbox. Full refresh of an identical identity tuple is not continuity evidence.
8. A tracked key remains protected while any corresponding Active or Retiring entry exists. `complete_retire` removes it only after the existing exact release proof succeeds. A same-number replacement Active+old Retiring pair stays deduplicated as one key.

Mailbox drain snapshots `(slot, window, destroy_stamp, event_time)` and marks that slot in flight. The subsequent graph `note_destroyed` may call a clock callback, which can reenter `note_hint`; a same-key newer destroy merges into the still-reserved in-flight slot, and other tracked keys already have union-reserved slots. On successful graph result, clear only if the live slot still has the same HWND and exact snapshotted stamp. A newer event remains queued. QueueFull/unexpected failure clears nothing. The in-flight slot is never reused before this comparison. Each invocation processes at most129 entries, counts reentrant additions within that budget, and stops on the first QueueFull/backpressure condition; each item does one bounded graph call. Stamp exhaustion is fatal ordering failure: preserve evidence and stop new graph admission/callback-capable work, retaining host resources.

The owner loop must call the synchronization/preparation boundary before it performs external graph mutations or resumes arbitrary message dispatch. Only exact-proof `complete_retire` is permitted externally and it removes tracked state; every admission/flush operation is observer-owned and prepared internally. These calls do not claim asynchronous ownership or host drain.

## Lifecycle and epoch boundary

Stop/EOF do not clear mailbox, tracked graph state, or old native ownership. Same-epoch restart reuses the immutable graph/epoch only after stop has invalidated all Active and Deferred state before unhook; old Retiring resources remain until exact proofs, and fresh native queries are required after hooks restart. A changed token, disconnect, Closed phase, observer stop or successful transport close is not host drain proof.

Protocol v2 has no accepted host-drain receipt, and peer/registry APIs do not synthesize one. This contract defines no mailbox reset or graph reuse for a fresh epoch. The old peer, graph, observer/mailbox, descriptor registry, mapping backing and native resources stay retained until a separately accepted external host-drain gate exists. The only later epoch transition is construction of distinct new peer/graph/observer/registry objects and distinct backing after old producers/I/O callbacks are quiesced and that external gate authorizes old-resource release. No existing v2 event or timeout meets this gate. Without it, quarantine and retain; do not reclaim by timeout or EOF.

This protects delivered WinEvents for graph-tracked Active/Retiring HWNDs and an in-flight candidate. It cannot detect an OS-dropped callback, an identical-tuple recycled HWND after destroy evidence is lost, or a destroy delivered before an untracked HWND enters an offer. Those limits remain distinct; overflow recovery is never presented as continuity proof.

## Acceptance tests

- Fill all 512 ordinary entries with unrelated child hints; deliver Destroy for tracked Active HWND. Verify mailbox admission succeeds, ordinary overflow/full refresh leaves it untouched, and graph eventually records the destroy once.
- Repeat with a pending protected destroy before child overflow and with a full graph ring. Verify bounded drain returns backpressure, retains every key, prevents the next query/admission, and resumes only after graph-event drain.
- Churn more than129 distinct HWNDs while withholding event drain. Verify reservation stops before the pending/tracked/candidate/post-admission union can exceed129; no mailbox overwrite occurs and no operation proceeds without its reservation.
- With64 Free graph slots and64 historical pending HWNDs disjoint from a new candidate, verify `64 + candidate + 64` is admitted exactly at the 129 bound. With65 historical pending HWNDs, force QueueFull during drain and verify the parent offer is rejected before any lookup/mutation. Then drain and prove a successful parent offer can flush64 Deferred descendants; the post-mutation snapshot plus old pending keys fits the reserved bound before any callback/query.
- Use fewer Free slots and a mixture of current Active/Retiring keys, old pending keys and candidate to verify exact pre-mutation free-slot bound; retirement does not count as a slot freed before proof.
- Reenter a newer Destroy for the same in-flight mailbox key from a test clock callback. Verify an old success clears only the snapshotted stamp and leaves the newer stamp. Verify QueueFull leaves old/new evidence intact.
- Offer a parent that flushes a multi-level Deferred subtree. Verify the post-mutation snapshot protects every newly Active child before next native work. Reenter Destroy during app-key lookup and verify candidate reservation retains it.
- Exercise a numeric HWND with old Retiring and new Active generations. Verify one protected key targets current graph state and remains until the final exact retirement completion.
- Promote an ordinary queued destroy as a key becomes tracked; prove mailbox admission precedes clearing the ordinary copy.
- Verify child-only non-destroy floods use no mailbox slots and cause no graph generation churn. Untracked destroy remains ordinary until candidate preparation.
- Verify foreign-thread hints are rejected before either table changes; accepted callbacks allocate nothing and wait for nothing.
- Verify same-epoch stop/restart retains evidence. EOF/Closed and stop cannot reset epoch; absent external host-drain gate, old objects/backing remain retained and fresh epoch reset is unavailable.
- Inject snapshot failure, invalid count, impossible reservation, QueueFull and stamp exhaustion. Verify no partial tracked-set update or evidence clearing, and no new operation crosses backpressure.

## Normative amendment: binding, external mutation, and failure retention

This section supersedes earlier wording that allowed arbitrary external graph mutation followed by `window_observer_sync_tracked`. A post-mutation sync cannot reserve mailbox headroom before a mutation that admits or flushes graph entries. Therefore, once a graph is bound to an observer, the observer is the exclusive owner of every graph operation that can admit an Active entry or flush Deferred entries. Coordinators must not call `observe`, `refresh_offer`, `refresh_commit`, `note_destroyed`, or any other admission-capable graph API directly. They must route those operations through observer-owned processing, which prepares the union/free-slot reserve before the first callback-capable query or graph mutation. Direct coordinator `complete_retire` is allowed only after the graph's existing exact release proof; it cannot admit entries. Immediately afterward, before another callback-capable call, the coordinator must call `window_observer_sync_tracked`. `invalidate_all` and all other graph mutations are observer-owned. If a future coordinator requires external admission, it needs a separately reviewed pre-admission reservation API; after-the-fact sync is insufficient and does not authorize it.

Binding is immutable for the observer lifetime. `window_observer_bind_graph` must run in Created before `start`; it snapshots and validates the exact graph/epoch before storing either. The graph pointer is borrowed and must outlive the observer. `start` is rejected until binding and initial synchronization succeed. Pump/refresh calls that continue to accept graph and epoch arguments must match the stored pointer and epoch exactly. There is no detach, rebind, or implicit epoch reset. Replacing a stopped observer is permitted only after the old observer meets the local quiesced-destroy rule below; a different epoch additionally requires a new graph/backing and the separately accepted external host-drain gate. Protocol v2 has no such receipt, so it does not permit that reset.

`Starting` is a callback-accepting observer state. Before installing the first WinEvent hook, start publishes the callback target and enters Starting. In Starting, every Destroy for a currently tracked HWND and for the current candidate uses the protected mailbox. Ordinary hints may be coalesced into the existing refresh latch. Started is published only after all required hooks install. On partial-install failure, hooks are removed while the callback target remains published; delivered protected destroys remain queued. If rollback removes all hooks, start returns to StoppedBound after clearing the callback target and waiting for in-flight callbacks; the mailbox is retained for retry. If any hook removal fails, the object enters FailedHooks, retains the target and hook tokens, accepts only protected Destroy evidence, and can be stopped/retried. Normal stop follows the same ordering: enter Stopping, keep accepting protected Destroy while removing hooks, then clear the callback target and wait for callbacks only after every hook is removed. If removal fails, enter FailedHooks without clearing the target. This closes the install/unhook interval without pretending that a full refresh identifies HWND incarnations.

An unexpected snapshot failure after a graph mutation, or any impossible snapshot count/reservation inconsistency, permanently latches `tracking_fault`. This is not a recoverable backpressure result. The callback target must remain lifetime-safe until hooks are removed; callbacks may only set/preserve the fault and protected evidence and must not initiate admission, release, or reclamation. The coordinator enters quarantine: it performs no further graph admission, slot release, mapping release, or old-bundle destruction, and retains the graph, observer, mailbox, mappings, and native resources. Repeated sync/pump calls return TrackingFault with no state/output mutation. There is no clear-fault or reset API. This terminal retention is fail-closed service loss; it is not a claim that all delivered destroys were processed.

Observer destruction is local and proof-bounded. It is allowed only after state StoppedBound, every hook token is absent, callback target is unpublished, in-flight callback count is zero, `tracking_fault` is false, the protected mailbox is empty, and a successful graph snapshot reports no Active or Retiring HWNDs. Otherwise it returns `ProtectedStatePending` or `TrackingFault`, leaves the caller's observer pointer and all state unchanged, and retains ownership. Successful destroy frees only observer-owned storage and nulls the caller's pointer; it never frees/unmaps the borrowed graph or mapped backing and does not assert host drain. Poisoned observers cannot be destroyed through this API. The old owner bundle must remain retained until an external teardown gate separately authorizes it.

The accepted implementation must add regressions for: (1) bind/snapshot before hooks and start rejection when unbound; (2) install-hook reentrancy delivering Destroy for a tracked HWND, retained after successful start; (3) the same event followed by partial-install failure, rollback retry, and restart; (4) Destroy reentrancy during unhook, retained on successful stop and failed removal; (5) failed post-mutation snapshot followed by additional callback delivery, proving permanent poison and no release/admission; (6) graph/epoch mismatch and forbidden direct-admission documentation; and (7) destroy rejected with hooks, inflight callbacks, pending mailbox, poison, or Active/Retiring entries, while successful local destroy leaves the borrowed graph untouched and makes no host-drain claim.

### Stop/restart gap amendment

A stopped interval has no hook coverage, so retaining an empty mailbox is not enough to claim incarnation continuity. Before removing the first hook, `window_observer_stop` must call the bound graph's atomic `interop_window_graph_invalidate_all` while the callback target is still live. That operation retires every Active entry and clears all Deferred records; it does not release any Retiring entry or backing. If the graph ring cannot hold the complete invalidation cascade, stop returns the existing GraphQueueFull status before changing observer lifecycle or hooks; the coordinator drains events without releasing surfaces lacking their exact proof, then retries. Once invalidation succeeds, admissions are disabled for the entire stop/unhook interval. Destroy callbacks delivered while removing hooks are still recorded, but they can only affect old Retiring entries and cannot re-admit cached facts. On restart, the same immutable graph/epoch is re-snapshotted before hooks and every new Active entry comes from a fresh native query after hooks are installed. This is a fresh observation, not continuity across the gap. Old Retiring entries and their mappings remain until their own exact release proofs. No host-drain proof is inferred.

Binding a new observer to a graph also performs this same pre-hook invalidation before it can become bound. It is the only safe way to attach when the graph may contain Active or Deferred state from an observation interval this observer did not cover. QueueFull is a retryable no-binding result with graph unchanged. After successful invalidation, snapshot and immutable binding are committed before returning. If that post-invalidation snapshot unexpectedly fails, the new observer is permanently TrackingFault and the coordinator retains the complete graph/native owner bundle. A coordinator must not capture or publish from the graph while bind or stop is incomplete.
