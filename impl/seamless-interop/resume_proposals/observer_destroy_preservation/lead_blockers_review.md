# O5 protected-Destroy contract blockers

The proposal has a workable core, but it is explicitly advisory: `STATUS.md:3-8,17-21` says only the graph snapshot is frozen and requires a consolidated normative observer contract before source work. Do not treat `contract.md`, `api.md`, or `cleanup_api.md` as accepted behavior yet.

## Decisions required before coding

1. **Freeze one graph snapshot ABI.** `api.md:32-38` proposes mutable graph plus `size_t` capacity/counts. The existing frozen API is `const interop_window_graph_t *` plus `uint32_t` capacity/counts in [`interop_window_graph.h`](/home/dev/Waddle-LSW/include/waddle/interop_window_graph.h:1284), and the implementation validates the complete claimed array span in [`window_graph_abi.zig`](/home/dev/Waddle-LSW/src/interop/window_graph_abi.zig:675). Observer code and tests must use that exact ABI. The mathematical properties needed by O5 are already implemented: sorted unique Active/Retiring HWNDs, exact Free-entry count, Deferred excluded, unchanged outputs on non-Ok.

2. **Name the mandatory callback-dispatch safe point.** `contract.md:15-29,33-44` proves 129 only when every callback-capable operation/admission is prepared. It does not give the coordinator an explicit operation that must run before the owner message loop dispatches WinEvent callbacks. `note_hint` cannot drain or wait inside the callback. Before yielding to arbitrary owner-thread message dispatch, the coordinator must call a bounded `prepare_callbacks`/`prepare_graph_mutation` operation that guarantees `|pending HWNDs ∪ Active/Retiring HWNDs| <= 129` (plus the current candidate and exact Free-slot headroom where an admission follows). If it cannot establish the reserve, the coordinator must keep dispatch/admission behind its scheduling boundary and drain/retry. State what the callback does on an unexpected mailbox-full or stamp-exhaustion condition: latch permanent `TrackingFault`, set `evidence_incomplete`, stop publication/admission/release, and retain the old bundle. Because a finite stamp or mailbox cannot preserve an event that arrives after its invariant is already broken, the claim must explicitly exclude post-fault delivery rather than say every Destroy is always retained.

3. **Specify promotion of already queued untracked Destroy hints.** `note_hint` cannot know a future candidate; Destroy for untracked/Deferred keys stays in the ordinary FIFO (`contract.md:35,65`). Before querying/offering an ordinary dirty candidate, promote and apply its queued Destroy before using facts. After a parent offer flushes Deferred children, promote Destroy payloads for all newly tracked children before the caller can consume graph events or capture. `contract.md:38` mentions promotion only when a “normal dirty record becomes tracked,” which does not state the refresh-enumeration or multi-child Deferred-flush ordering. Add regressions for both and preserve the ordinary copy until mailbox insertion succeeds.

4. **Freeze the event-consumption barrier across a reentrant commit.** `contract.md`'s reentrant section correctly distinguishes `query_facts` (apply Destroy before offer and discard facts) from app-key lookup (observe may commit first). The latter requires the coordinator to stage graph events and suppress pending-key Announce/Update until post-call Destroy resolution and fresh native validation. The proposal names a queue “at least one full graph-ring capacity,” but successive ring drains can exceed that bound while the destroy remains blocked. Define who owns the staging storage, its fixed bound, when graph admissions stop before it fills, how order is kept, and which API tells the coordinator which HWND barriers remain. `destroy_pending` is proposed in `api.md:105-119`, but its lifecycle/error semantics and the required stage-before-drain order are not frozen. Deferred children also need fresh native validation before capture; neither the snapshot nor mailbox reserve proves cached facts are live.

5. **Freeze start/stop ordering and partial-unhook ownership.** Current source contradicts the requirement: [`window_observer_windows.c`](/home/dev/Waddle-LSW/src/interop/window_observer_windows.c:525) clears the active callback slot before unhook, then erases the dirty queue; [`window_observer_windows.c`](/home/dev/Waddle-LSW/src/interop/window_observer_windows.c:603) publishes hooks while state remains Created, and `note_hint_active` rejects callbacks unless state is Started at lines 696-698. Thus reentrant install/unhook Destroy callbacks are discarded today. Normative state transitions must set Starting before first install; retain target while any token remains; set Stopping before unhook; and set StoppedBound only after all hooks are removed, target unpublished, and callbacks quiescent. On partial start rollback or stop failure, specify exactly which tokens remain, that only stop retry is allowed, and that protected Destroy remains accepted. On retry after a successful invalidation, do not clear the mailbox or reinitialize stamps. Stop QueueFull must happen before any lifecycle/hook mutation; successful `invalidate_all` leaves every old resource Retiring until exact release proof.

6. **Choose destroy side-effect semantics and a zero-leak poison cleanup path.** Existing `window_observer_destroy` implicitly calls stop (`window_observer_windows.c:560-583`). `cleanup_api.md:115-138` recommends either explicit stop before destroy or a documented retained-handle result after stop side effects; choose one. Normal destroy must not free a graph, Retiring entry, mapping or backing. `cleanup_review.md:5-15` correctly identifies that forbidding destroy on TrackingFault without transfer leaks the observer allocation. Freeze and implement the separate quiesced evidence handoff before enabling poison paths, or explicitly obtain a policy exception. The `cleanup_api.md` handoff currently remains suggested, not accepted; freeze record layout/version/capacities, complete dirty and destroy evidence, candidate/fault fields, in-flight representation, all pointer-span/alias checks, exact status/output atomicity, and the conditions under which it may free only the observer allocation. It must be impossible while any hook, target or in-flight callback remains. The handoff record is evidence only: no restore, reset, release, or host-drain authority.

7. **Align lifecycle/API compatibility.** `api.md` appends statuses 16-18 and reuses Created/Stopped with bound flags while adding Starting/Stopping/TrackingFault states. Confirm numeric values against the current enums, exact error precedence for graph-pointer/epoch mismatch versus NULL/invalid output, whether all old pump/refresh signatures remain and reject any non-bound graph/epoch before clock/callback/output, and what `destroy_pending` reports in StoppedBound/FailedHooks/TrackingFault. Requiring bind before start is behavior-breaking even if signatures remain source-compatible; update every caller in the same acceptance slice. Keep graph pointer borrowed and immutable for the observer lifetime.

## Capacity review

The core bound is sound under its stated invariants. Active+Retiring entries share 64 graph slots, the exact Free count is exposed by the already-frozen snapshot, and one admission/flush can add at most `F` unique tracked HWNDs. With `U = pending ∪ tracked ∪ candidate`, `|U| + F <= 129` reserves enough mailbox keys for old pending evidence plus every new entry admitted from Free slots. During a clock callback in `note_destroyed`, new destroys for tracked/candidate HWNDs merge into keys already in `U`; clear only an unchanged `(HWND, stamp)` after graph acceptance. `complete_retire` can only reduce tracked membership. This proof fails immediately if a coordinator bypasses the observer, fails to reserve before callback-capable calls/message dispatch, or clears on QueueFull. The proof also needs the dirty-to-protected promotion rule above so a Destroy for a Deferred child delivered before its parent flush is not left behind the new graph event.

## Recommended bounded implementation split

1. Freeze the normative O5 header/spec with the exact existing graph snapshot ABI, state/status values, callback-dispatch reserve API, mailbox overflow/stamp-fault behavior, promotion ordering, and a chosen destroy/handoff contract.
2. Implement the observer-local layer only: immutable graph bind + initial invalidate/snapshot; 129-key mailbox and reservation; Starting/Stopping callback behavior; observer-owned admission/refresh wrappers; post-mutation snapshots; fail-closed poison; stopped protected-Destroy drain; exact local quarantine handoff. Test with fake hook/query/clock callbacks, especially reentrant start/unhook/query/app-key/clock and QueueFull rollback. Do not claim coordinator safety yet.
3. In a separately reviewed coordinator integration, enforce the safe point before message dispatch and admissions, stage graph events under a fixed capacity/backpressure rule, suppress capture/publication behind per-HWND Destroy barriers, and fresh-query Deferred children. Then add native Windows Create/Destroy hook qualification. Keep Retiring backing until existing exact capture/registry release proof; neither stop, mailbox drain, EOF nor handoff releases it.

This review is read-only. I made no repository edits and ran no tests or builds. No observer/O5 behavior should be marked accepted or complete from these advisory files alone.
