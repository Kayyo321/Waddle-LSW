# Priority-destroy lifecycle/cleanup review

The central preservation rules are sound: stop must invalidate Active/Deferred graph state before unhooking, keep the callback target published while hooks are being removed, wait for in-flight hints only after the last hook is gone, and preserve the protected mailbox across stop/retry. This prevents a stopped gap from being mistaken for continuity and avoids dropping Destroy callbacks delivered reentrantly during unhook. In particular, current `stop_locked` in `src/interop/window_observer_windows.c` calls `release_slot` before `remove_owned_hooks`, then clears `dirty_count`; that ordering cannot implement the proposed contract and would need replacement. The graph/backing stays borrowed and must never be freed by observer teardown.

## Blocking cleanup ambiguity: TrackingFault

As written, permanent `TrackingFault` forbids `window_observer_destroy`, with no clear/reset or evidence-transfer operation. That creates an observer-local allocation with no deterministic release path, even in cases where releasing that allocation is safe and does not release the graph or backing.

A concrete case is `window_observer_bind_graph`: `invalidate_all` succeeds, then its callback-free snapshot fails. The contract requires a terminal fault and retention of the graph/native bundle, but the observer is still Created and has never installed hooks, published a callback target, or admitted an in-flight callback. Its own allocation can be freed safely; only the borrowed graph and native resources must remain quarantined. The current prohibition intentionally strands the observer allocation.

A second case is a runtime post-mutation snapshot fault followed by successful removal of every hook, unpublication of the callback target, and `g_hint_inflight == 0`. The graph/backing still must remain quarantined and the mailbox evidence still matters, but the observer's C allocation is not itself mapping backing. The current API offers no way to detach/copy the mailbox into the coordinator's retained quarantine bundle, so it requires retaining the entire observer forever. That is fail-closed, but it is an intentional process-lifetime allocation, not a deterministic cleanup path, and conflicts with the repository's zero-leak lifecycle rule unless explicitly accepted as a bounded quarantine exception.

Recommended lead decision: keep graph, mapping, mailbox evidence, and native backing retained, while separating observer-local finalization from those resources. Either (a) add an output-preserving, caller-owned fixed-capacity quarantine snapshot/handoff for the mailbox and fault diagnostics, callable only after all hooks are absent, callback target is unpublished, and in-flight count is zero; then allow freeing the observer allocation without touching graph/backing; or (b) explicitly define the observer allocation itself as a process-lifetime quarantine owner and document that exception to deterministic deallocation. Merely allowing destroy on poison is unsafe because it would discard the only mailbox copy. Never free graph entries or release/unmap surfaces as part of this local finalization. The handoff must not claim host drain and must not make graph reuse/epoch reset available.

Hook removal failure remains a hard local barrier: the active target and observer allocation must stay valid because callbacks may still arrive. Likewise, while any callback is in flight, local finalization is forbidden. Once all hooks are removed and the active target is unpublished, `release_slot`'s in-flight wait is the relevant local quiescence proof; it is not proof that the graph or native resources can be reclaimed.

## Stop and pending evidence

The contract consistently says stop preserves mailbox evidence and does not release Retiring resources. It should specify how already-pending mailbox items are applied when the observer is `StoppedBound`: existing pump/refresh are Started-only, while destroy is prohibited until the mailbox and tracked graph are empty. Re-starting and then pumping could eventually drain the mailbox, but that recovery route is not stated as a required transition and may be undesirable after the caller intended permanent stop. Add either a callback-free `drain_pending_destroys` operation valid in StoppedBound/FailedHooks after its graph/epoch preflight, or explicitly require same-binding restart solely to drain preserved evidence before final local destroy. Neither route may clear mailbox entries without the exact `note_destroyed` acceptance already specified. It is correct that stop itself must not clear these entries.

The stop QueueFull transaction is implementable: `invalidate_all` must be all-or-nothing, and QueueFull returns before state/hook/target changes. After successful invalidation, the unhook path must retain the target through all remove attempts; on any failed removal, retain the failed token(s), target, mailbox, and Retiring graph state. On retry, remove only remaining tokens, then unpublish and wait. Ordinary hints may be discarded/coalesced according to the stated stop behavior, but protected destroys cannot be cleared in rollback or restart initialization.

## Other precise boundary notes

- `window_observer_destroy` can prove only local hook/callback quiescence plus mailbox/graph-list emptiness. A zero Active/Retiring snapshot is not a host-drain receipt and must not authorize freeing descriptor/mapping backing held by the coordinator.
- The proposal's normal local destroy can safely free the observer after proof while leaving the borrowed graph untouched. Clarify that graph lifetime is independent: the graph may remain allocated with no observer, and its backing owner still controls retirement/release.
- Bind/stop post-invalidation snapshot failure is not a rollback case: invalidation already mutated graph state. Do not report graph unchanged or allow rebind. Preserve the graph/native owner bundle; decide explicitly whether the observer-local allocation follows the quarantine-handoff rule above.
- Destroy-callback capacity exhaustion cannot overwrite mailbox evidence. The reservation proof must establish that tracked/candidate callbacks can merge into an existing key or have a reserved slot before any operation/message-dispatch boundary; otherwise TrackingFault cannot itself preserve a destroy that arrives after the mailbox is full.

This is a proposal-level review only. I made no repository edits and did not run builds or native tests. It does not validate host-drain proof, installed-session callback delivery, or implementation feasibility of the broader observer/graph integration.
