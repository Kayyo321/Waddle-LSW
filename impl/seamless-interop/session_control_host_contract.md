# Control-Only Host Runtime Contract

## Scope and ownership

`session_control_host` is a synchronous Linux host control runtime. With no feature table it is a capability-zero diagnostic runtime. It joins the existing bounded session admission entry, explicit backing mapping owner, and existing Linux socket owner. The latter already owns the protocol peer and connected transport. `interop_host_control_owners_t` deliberately exposes the authentic session owner and mapping owner separately so a failed cleanup never hides or discards ownership.

`session_main` accepts exactly one mode with `--device NAME`: `--control-only` (one bounded session) or `--supervised` (reconnecting supervisor over session_app, see `claude_45_percent/session_app_contract.md`). It also accepts optional `--backing-kind file|kvmfr` (default `file`), optional `--run-for-ms N` (default 30000, range 1..120000), and, with `--supervised` only, `--max-retries N` (0 means unlimited). It resolves only an existing healthy device profile, reads its selected profile configuration, and uses that configuration's `av_shm_path`. It does not ensure or spawn a daemon, start or stop a guest, create or truncate a backing object, modify a legacy AV path, or infer a backing kind from the path or `stat`. `file` and `kvmfr` are explicit choices; the mapping owner independently validates the selected descriptor facts. The profile must have AV mapping enabled and a configured path.

The runtime configuration borrows the already-connected daemon control descriptor, already-open read/write backing descriptor, stop descriptor, version bytes, and device profile. The runtime does not close those descriptors. The stop descriptor must be distinct from the daemon and mapping descriptors, and must already have both `O_NONBLOCK` and `FD_CLOEXEC`; the runtime never changes flags on caller-owned descriptors. The selected-device daemon endpoint is a caller precondition: peer UID validation establishes same-euid locality, while the path/config selection establishes which device's daemon is being addressed. It owns newly acquired session/AV leases, connected peer/socket, protocol peer allocation, and mapping owner. Any failed cleanup leaves each authentic owner in the caller's explicit output slots. `interop_host_control_retry_cleanup` may retry local cleanup only after `run` returned and all local users have stopped.

## CLI lifecycle

The CLI validates exact option spelling and bounded decimal values, resolves the selected device by a read-only registry scan, requires its parsed configuration to be valid, and loads the device-specific config path. It blocks SIGINT/SIGTERM on the main thread and uses a nonblocking close-on-exec signalfd as both admission cancellation and event-pump stop input; it restores the prior signal mask on every exit. It obtains one nonzero token from `getrandom`, uses the compiled local agent version, advertises exactly zero capabilities, opens the configured backing path without `O_CREAT`, and connects to the selected daemon Unix socket with nonblocking connect/poll under one finite connection deadline. The daemon control descriptor remains borrowed by the runtime. The admission deadline is bounded independently at 120 seconds; `run_for_ms` starts after admission succeeds and is an additional post-admission diagnostic bound.

The CLI labels this run `RuntimeControlOnly`. It does not present capture, compositor, Wayland, audio, input, or feature-module functionality. Capability-zero Ready means only protocol control readiness.

## Admission, mapping, and pump sequence

1. Call `interop_host_session_admit` once with the selected device, connected daemon fd, cancellation descriptor, one absolute 120-second monotonic deadline, nonzero token, local capabilities zero, and bounded GuestReady/drain values. The entry checks daemon peer credentials, Running/status profile, GuestReady, and performs exactly one VSOCK attempt. Failure never reconnects.
2. Create a mapping owner and open the caller-selected existing descriptor with the explicit backing kind. This maps the existing exact 2 GiB object without initializing or writing bytes. The mapping header remains unvalidated until the peer reports Hello's actual nonzero epoch.
3. On the creating pthread, ask the existing socket owner for poll interests and a timeout. Poll its borrowed fd, the borrowed daemon control descriptor, and the signalfd. Clamp each wait to 100 ms and the post-admission deadline. The daemon control stream is readiness-only after admission: HUP/ERR initiates drain; unexpected readable bytes terminalize the diagnostic run and are never fed to the interop peer.
4. Drive the socket owner with its current poll cookie, current monotonic time, bounded RX/TX/syscall budgets, and fixed frame buffer. It feeds the existing protocol peer; its returned event is handled before the next poll.
5. For `ValidateMapping`, use the event's Hello epoch with `interop_mapping_linux_validate_header`. This snapshots and validates the actual mapped header via the layout validator, including the epoch and lock-free atomics. Publish the borrowed mapping view and only then call socket `mapping_result` with success. A failed validation reports mapping failure and never acknowledges Hello. Header immutability from guest initialization through Hello/Ack is a protocol precondition.
6. For `Ready`, require negotiated capabilities to equal zero. Only after Ready, every 500 ms, read and increment the host heartbeat through `interop_heartbeat_load` and `interop_heartbeat_store_next`; no ordinary memcpy or raw heartbeat atomic access is allowed.
7. With `feature_ops == NULL` (capability-zero), any `FeatureFrame` is unexpected: begin bounded drain and return a feature error; never dispatch or silently discard the copied frame. With a feature table, frames are dispatched as described in the feature section below. Peer Draining and transport terminal states are handled as control outcomes only.
8. On SIGINT/SIGTERM or the post-admission run deadline, call socket `begin_drain` and continue pumping only bounded Goodbye/control TX until the socket owner closes or its drain deadline expires. If the run deadline arrives before Ready, return `HostControlTimedOut`; the later completion of a control drain cannot turn an incomplete handshake into success. Once draining, poll waits use the socket owner's bounded drain interval (still clamped to 100 ms), not the expired run deadline. Daemon stream HUP/ERR also initiates this control-only drain. The single synchronous pump is the sole mapping view user, so after it stops accessing the view, it may call mapping close with truthful `local_users_quiesced=1`; this statement proves only local users stopped.
9. Destroy mapping and socket/peer owners, then release session and AV leases. Preserve any authentic owner if cleanup fails. `interop_host_control_retry_cleanup` leaves owners published after every unsuccessful retry. The standalone `waddle_session_main` CLI retries once and, if authentic owners still remain, calls `_exit(1)` at the process boundary rather than returning and discarding those pointers; this is process termination, not a claim that a retry succeeded or a normal cleanup proof. Embedders must retain the owner pair and retry themselves. Local socket EOF, Goodbye, cancellation, timeout, lease release, or unmap does not prove guest memory detach, peer drain, compositor release, or safe backing reuse.

## Errors and verification boundary

Invalid CLI options print help/usage without connecting. The exported `waddle_session_main(argc, argv)` is a process-main-thread entry intended to be called once; `argv` remains caller-owned and borrowed only for the call. It returns 0 after a bounded clean run, 2 for argument/profile errors, and 1 for runtime/OS failures. Missing/unhealthy device, invalid profile config, absent mapping path, unsupported mapping kind, missing daemon socket, invalid backing metadata, wrong Hello epoch/layout, unexpected feature frames, daemon HUP/data, timeout, signal, transport error, and cleanup failure each produce a nonzero process result (the runtime API gives the specific enum). There is no implicit daemon spawn, reconnect, guest lifecycle operation, or backing creation.

Tests must exercise the real CLI parser/help/invalid inputs and the exported runtime with AF_UNIX daemon/socketpair peers, a real 2 GiB sparse regular file, a real `interop_mapping_linux` owner, real `interop_linux_socket`/peer protocol, valid Hello/Ack/Ready exchange, stop/drain/cleanup, and injected transport, mapping, timeout, signal, and cleanup failures. They must not claim live Windows or real AF_VSOCK acceptance. Normal, ASan/LSan/UBSan, and at least 90% production line and taken-arc coverage are required.

The runtime establishes no remote peer-drain, mapping detach, Wayland/compositor buffer release, capture pin release, guest epoch-reuse, or backing-object reuse proof. It intentionally advertises no feature capabilities and provides no application-facing feature dispatch.

## Feature table, detail output, and graceful stop

These rules apply only when `interop_host_control_config_t.feature_ops` is non-NULL. The capability-zero wording above holds only when feature_ops is NULL.

- **Validation.** Before any admission, the table's `local_capabilities` must be within the capability mask and equal the admission offer. `poll_fds` and `on_fds` must be both set or both NULL. `interop_host_control_run` returns InvalidArgument for a NULL or misaligned table, and the same for a re-entrant call from a callback.
- **Callback scope.** The sender API (`interop_host_feature_send`, `_send_request`, `_release_request`) is valid only inside callbacks. Callbacks run on the pump thread and never re-entrantly. `poll_fds` and `next_deadline_ms` also run under the re-entry guard, so calling `interop_host_control_run` or `interop_host_control_retry_cleanup` from them returns InvalidArgument.
- **Closing.** `on_closing` runs exactly once per run. It also runs when a refusal follows table validation (device check, stop-descriptor flags, zero token), so a validated table is always told that the run ended. Every sender call after closing begins returns Draining.
- **Remote Error.** A remote Error with request identifier zero, or any Error received before Ready, is fatal: the run records PeerFailed, sets `detail->guest_error`, and drains. A remote Error with a nonzero request identifier received while Ready is non-fatal. It is delivered to `on_peer_error(error_code, request_id, sender)`, and its result follows the normal settle rules: zero continues, `InteropHostFeatureStopRequested` ends the run as Cancelled, any other value fails it.
- **Feature descriptors.** `poll_fds` may supply at most `InteropHostFeatureFdCapacity` entries. A supplied descriptor equal to the socket, stop, or daemon descriptor fails the run with FeatureFailed before polling; negative entries are ignored. After a poll, a feature descriptor with POLLERR, POLLHUP, or POLLNVAL fails the run with FeatureFailed before `on_fds` is considered. `on_fds` is withheld once drain has begun, including a same-iteration peer Draining event or a fatal Error.
- **Cookie after drain.** A feature-initiated drain that starts after the socket poll cookie is taken refreshes the cookie before the socket drive. Otherwise the drive would use a stale cookie and drop the Goodbye.
- **Graceful stop.** A feature callback returning `InteropHostFeatureStopRequested` begins drain and ends the run as HostControlCancelled. Other nonzero values fail the run as HostControlFeatureFailed. Every ops callback still receives `on_closing` exactly once.
- **Detail.** `interop_host_control_run_detailed` fills an optional `interop_host_control_detail_t`: `admission_result` (the session-layer result when admission was refused), `reached_ready` and `ready_at_ms` (monotonic time of Ready), `guest_error`, and `ended_at_ms` (monotonic time at cleanup). A failed monotonic read at cleanup stores zero. `interop_host_control_run` is the same with a NULL detail.
- **Identifier classes.** Request identifiers are owned by the peer (`enqueue_request`/`release_request`). Inbound frames are checked by class: Unsolicited types carry zero, Request types carry a nonzero identifier allocated by the remote requester, and Response types carry a nonzero identifier that is a live local reservation whose request type maps to that response. A violation is answered with Error(ProtocolViolation), the peer drains, and the run reports the violation as a Draining event with that error code.
