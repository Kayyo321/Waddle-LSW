# Graph HWND incarnation and OwnerHidden review

Read-only review of `impl/seamless-interop/claude_window_graph/IMPL_DESC.md`, `impl/seamless-interop/CLAUDE_HANDOFF.md`, `src/interop/window_graph.zig`, and the observer contract. No repository files were changed and no builds were run.

## O5: overflow can permanently retain a recycled HWND

**Finding — accepted risk is real and is broader than an external OS-loss caveat.** The 512-key observer table deliberately drops the 513th distinct key and sets only a global overflow latch (`claude_window_graph/IMPL_DESC.md:620-627`; observer code comment at `src/interop/window_observer_windows.c:991-1001`). Recovery clears all dirty entries, including destroy data, then full-refreshes without invalidating (`IMPL_DESC.md:623-626`). When a destroyed top-level HWND was one of the discarded keys and is reused with the same `(process id, thread id, process start time, class hash)`, the refresh has no evidence that it is a new object, so the graph retains the old generation and surface indefinitely. The report explicitly pins this at `IMPL_DESC.md:626` / decision 30 at `1292`; observer header says the same at `src/interop/window_observer_windows.h:57-65`. The loss occurs even if Windows delivered the destroy callback; only external OS-loss is inherently outside the observer's control.

The alternative of calling `invalidate_all` on every overflow would eliminate the stale surface by retiring every graph entry, but it directly violates the stated no-churn requirement: normal child-control floods are known to overflow (`IMPL_DESC.md:622`, O24 at `1331`), and the existing regression expects 600 child destroy hints to cause no generation changes (`tests/interop/window_observer_windows.c:1087-1110`). Full refresh cannot distinguish “same object, many irrelevant child hints” from “one top-level destroy hint was dropped and its HWND recycled.” Thus no global policy can guarantee both zero stale reuse and zero overflow churn with only the present overflow bit and identity tuple.

**Recommendation:** do not silently broaden acceptance by calling this merely unavoidable OS uncertainty. Keep full-refresh/no-churn as the default only with an explicit residual-risk decision, and separately preserve destroy evidence for currently exported HWNDs across generic-table overflow. A bounded design can exploit the graph's hard maximum of 64 non-Free entries: maintain a fixed, callback-readable set of currently exported HWND keys (updated by the owner thread from graph outcomes) and a separate per-key pending-destroy cell/queue for those keys. A matching destroy must survive clearing the general 512-key hint table and be replayed through the existing timestamp/stamp rule before or during refresh. The callback must remain graph-free and nonblocking; the set update/read publication protocol needs a separately specified race-safe representation. This avoids routine child-hint floods churning every surface while closing the deterministic “our own full dirty table discarded a known exported window's destroy” gap. It does not solve an OS-dropped callback or exact-tuple reuse after the callback was never delivered.

If the coordinator cannot implement and natively prove that small priority path, the only strict fail-closed answer is to quarantine/reset the whole graph/session on overflow. That necessarily churns all surfaces on ordinary child floods, so it is a product decision rather than a safe transparent tweak. Do not claim a full refresh proves continuity for identical tuples.

**Unavoidable uncertainty:** even with the priority path, Windows may omit the destroy callback, and a recycled HWND can reproduce all four measured identity facts. `window_observer_windows.h:57-65` correctly documents that `SetProp` is not a safe unique token for foreign windows. A native same-tuple replacement cannot be distinguished from continuity using the frozen facts. If that threat must be eliminated, require a stronger OS-provided lifetime discriminator or fail closed on an independently detectable discontinuity; no portable tuple comparison or periodic refresh can manufacture that evidence.

**Tests to add if adopting the priority path:** (1) mark a graph-admitted HWND in the tracked set, fill the 512 general keys with child hints, deliver its destroy and then a same-tuple replacement, recover, and assert old generation retires/new generation is announced; (2) same flood without a tracked top-level destroy retains generations and emits no events; (3) callback racing owner-thread removal/re-registration cannot attach an old destroy stamp to the replacement key; (4) priority storage remains bounded at the graph's 64-entry maximum and drain/retry does not lose the pending destroy; (5) separate test records that no callback + identical tuple remains undetectable, rather than pretending a refresh resolves it. Native tests are essential for callback publication/race behavior.

## O25: deferred children can be promoted from the old incarnation

**Finding — fixable ghost-event path.** On an Active parent identity change, `observe_eligible` sets `ReasonIncarnationChanged`, collects only the Active cascade, and sets `redefer = false` (`src/interop/window_graph.zig:2168-2180`). But the replacement is still planned as an admission and `plan_flush` seeds *all* deferred records whose `parent_window` equals the raw HWND (`1895-1932`, called unconditionally for an admission at `2230-2235`). Deferred records carry `parent_generation = 0` and no generation/identity for their deferred parent (`claude_window_graph/IMPL_DESC.md:172-179`); the flush therefore assigns the new parent's generation to stored child facts from before the parent HWND changed identity (`apply_flush`, `1935-1965`). A stale deferred child can be announced as belonging to the new parent; later refresh may retire it, but the intervening Announce/RetireIntent is exactly the ghost pair documented at `IMPL_DESC.md:1332` (m5).

The current behavior is deliberate for same-incarnation Reclassified transitions: `IMPL_DESC.md:601` and decision 22 at `1284` say those descendants are alive and still owned, so they can be re-deferred/promoted. That rationale does not apply to `IncarnationChanged`.

**Minimal fix proposal:** when the primary HWND is replaced for `ReasonIncarnationChanged`, do not run the deferred-child flush for that admission. Also invalidate/drop the deferred subtree rooted at that raw parent HWND (direct deferred children plus deferred descendants reached through their `parent_window` links), counting these as deferred drops; otherwise a later admission of the same numeric parent HWND could flush the stale records. Re-observation/periodic refresh will requery still-live children and admit them against the new parent, while gone children disappear without a false Announce. Keep the existing flush/redefer behavior for same-incarnation Reclassified and ordinary first admissions. The bounded 64-record arrays allow this to be staged transactionally before retiring the old cascade, consistent with the graph's existing plan/apply pattern.

**Regression:** defer child C behind parent HWND P; offer a new identity tuple for P; assert P is re-admitted, no C Announce is emitted and old deferred subtree is dropped/quarantined; then offer fresh C facts and assert it is admitted against P's new generation. Add a chained deferred grandchild and ensure it is not later flushed from a second P reuse. Retain the existing same-incarnation Reclassified cascade tests to prove the fix does not break legitimate child promotion.

## OwnerHidden and `uac_mode` consistency

The semantics are internally consistent if the documented precondition holds: observer queries `owner_root`, overlays the same core flags, classifies it with observer `uac_mode`, and marks OwnerHidden only for Gone/NotExported (`IMPL_DESC.md:518-523`). The graph then treats it as unowned (`:375` and `:1282`). Both configs explicitly require equal values (`:151-153`), and startup instructions pass the graph's exact value into observer creation (`:1195-1198`; root handoff `CLAUDE_HANDOFF.md:110-114, 115-117`).

There is no runtime enforcement: `interop_window_graph_config_t` and `window_observer_config_t` are created independently, and observer creation has no graph handle to compare against (`IMPL_DESC.md:151-153`, observer create at `:446-449`). A coordinator bug can therefore construct a mismatch. For example, if graph mode classifies an owner as exportable but observer mode marks it hidden, a popup is exported as unowned; the inverse may leave a child deferred under an owner that the graph will never export. This is a caller-precondition/integration risk, not an inconsistency in the specified owner-query sequence.

**Recommendation:** keep the ABI unchanged and make the session coordinator own one validated `uac_mode` value used for both creates; add an integration/startup test that creates both components from that single configuration source and rejects out-of-range mode before either starts. If separate component configuration remains possible, add a coordinator-level equality check before `window_observer_start`; the observer API itself cannot verify equality without changing its boundary. The observer's unit tests should continue verifying the owner classification uses its mode; do not weaken the existing explicit equality contract.

## Expanded O25 audit: apply one deferred-subtree invalidation rule on every known parent discontinuity

The original O25 path is one instance of a more general invariant gap: a deferred record stores the numeric `parent_window` but no parent generation or parent incarnation. The graph must invalidate deferred descendants whenever it has accepted evidence that the keyed parent is gone, excluded, or replaced. Otherwise the same HWND can later become Active and flush records from the earlier key lifetime.

### Affected paths

- **Active parent replacement:** `observe_eligible` detects `!identity_equal` at `src/interop/window_graph.zig:2168-2180`, but `plan_flush` still seeds deferred children by raw `parent_window` at `:2230-2235` / `:1895-1932`. This is the O25 ghost Announce case already described above.
- **Deferred parent replacement:** when there is no Active entry, `observe_eligible` can find the parent's deferred record and set `plan.drop_d = true` on identity mismatch (`:2182-2183`). It then admits the new identity and flushes other deferred records waiting on that HWND (`:2230-2235`); `apply_eligible` drops only the replaced record at `:2288-2290` and flushes the other records at `:2304-2316`. Thus a deferred old parent can also promote stale deferred children despite there being no Active cascade. This is distinct from the existing test that only proves the reused *record's own key* is dropped (`window_graph.zig:7195`); it does not test records waiting on that reused key.
- **Accepted destroy:** `note_destroyed` applies a valid hint to an Active entry and `retire_cascade`s only Active descendants (`:2457-2470`), or drops the exact deferred record (`:2471-2474`). Neither branch removes deferred records whose `parent_window` equals the destroyed HWND, or their deferred descendants. If that HWND is admitted again later, an ordinary admission's `plan_flush` can promote them.
- **Exclusion/hidden:** `observe_not_exported` retires the Active cascade or drops the exact deferred record (`:2058-2073`) but leaves deferred children waiting on that key. A later eligible observation of the same numeric HWND can flush them. This applies to OwnerHidden-refined classification as well as class/UAC/visibility exclusion; this is a keyed graph relationship problem, not specific to one exclusion reason.
- **Refresh unseen:** `refresh_commit` stages the Active retirement set, then drops only deferred records with `seen == false` (`:2642-2670`). A deferred child of a doomed unseen parent can be marked seen by its own offer in the refresh and survive the commit, even though the parent was individually rechecked as Gone and is being retired. If the HWND is reused and re-admitted later, the same stale flush is possible. The parent-and-child case needs a regression where the child is offered/seen but the parent is absent/Gone.
- **Ignored/stale destroy hints:** do **not** invalidate on a hint rejected by the existing stamp/time rule (`:2458-2464`, `:2471-2474`): by contract it may refer to the previous incarnation, so it is not accepted evidence about the current graph identity. Likewise QueueFull must not apply any planned subtree deletion.

### Single bounded helper/mask contract

Add an allocation-free read-only planner over the fixed 64 deferred slots, e.g. `plan_deferred_subtrees(graph, root_windows, out_mask)`. It seeds every used deferred record whose `parent_window` is any invalidated root, then follows deferred parent links breadth-first: whenever a record is selected, add used deferred records whose `parent_window` equals that record's `window`. Each slot is selected at most once, so it terminates in at most `MaxDeferred` scans and never follows an unbounded chain. The separate root record itself is included only when the caller is removing/replacing that deferred parent; `plan_flush` already excludes `record.window == primary_window`.

Compute the mask before mutation, then apply it through the existing `drop_deferred` helper only after the caller's full failure preflight succeeds. Callers/root sets:

1. Active `IncarnationChanged` replacement: root = replaced HWND; suppress the deferred portion of the replacement's flush. This removes stale descendants; fresh observer offers can re-admit live children.
2. Deferred record identity mismatch: roots = that deferred parent's HWND; drop its direct/transitive waiting subtree and suppress any flush caused by its replacement.
3. Accepted `note_destroyed` match (Active or Deferred): root = destroyed HWND; apply after the current event-ring capacity check. Do not do this when the destroy was rejected as older than the admitted/deferred facts.
4. `observe_not_exported`: root = excluded/hidden HWND, whether the path is Active or removes its Deferred record; apply after the cascade event capacity check.
5. `refresh_commit`: roots = every Active HWND in the precomputed `doomed` set; combine the selected-descendant mask with the existing unseen-deferred-drop mask (union, count each slot once), and apply only after the RetireIntent ring-room preflight. This removes seen deferred children of parents confirmed absent, while already-unseen records remain covered by the existing behavior.

Preserve same-incarnation `Reclassified` behavior exactly: do not add its parent to the invalidation roots; its deferred children remain candidates for flush and its Active descendants retain the existing re-defer rules. `Suspended`, `Unchanged`, `Update`, failed observer queries/`refresh_keep`, and rejected stale destroy notifications are not identity-discontinuity evidence and must not trigger invalidation. `invalidate_all` already drops every deferred record.

### Failure atomicity and retry rules

The planner itself only reads graph state and writes a stack mask. It cannot mutate counters, event storage, or deferred records. Apply the mask only in each path's apply phase:

- `note_destroyed` and `observe_not_exported`: after validating the event-ring capacity for all Active cascade RetireIntents. If capacity is insufficient, return QueueFull with all Active/Deferred graph state intact (apart from the documented queue-full diagnostic counter).
- `observe_eligible`: after the entire retirement + replacement + valid-child flush ring-room preflight and after callback lookup outcome is known. A queue-full rejection leaves the old graph and deferred tree intact for retry. A lookup/capacity/generation failure after a positively observed identity change still retires the old incarnation as current contract requires; apply deferred invalidation even if the replacement is not admitted, because stale children cannot safely remain tied to the old key lifetime.
- `refresh_commit`: include only the new Active retirement events in its existing preflight. Deferred drops produce no wire events. If `needed > ring_room`, return QueueFull without applying either Active retirement or deferred invalidation; the open refresh may be drained/retried as today.

This preserves the event-ring transactional boundary and keeps the helper bounded/fixed-storage. Do not drop descendants during a preflight that may still return QueueFull, and do not make a stale/ignored destroy hint destructive.

### Required focused regressions

1. **IncarnationChanged Active parent:** Active P with a deferred child C and deferred grandchild D; change P's identity. Assert no Announce for C/D, no stale deferred subtree remains, and freshly re-offered C then D are admitted with the new generations. Keep the same-incarnation Reclassified test proving legitimate children still flush.
2. **IncarnationChanged Deferred parent:** defer P under absent ancestor A, defer C under P and D under C; offer new P identity while A remains absent. Assert old P/C/D records are invalidated, no C/D promotion occurs when P later becomes Active, and fresh facts can restore the live chain.
3. **Accepted destruction:** deferred P/C/D; send a destroy hint newer than P facts and within tick bounds; admit a replacement P and prove no stale descendants flush. Repeat with a stale hint and prove the graph state is unchanged.
4. **Exclusion:** Active P with deferred C/D, then offer P as a NotExported class/OwnerHidden case; re-admit numeric P and assert no stale descendants flush. Cover deferred P as well as Active P.
5. **Refresh unseen/Gone:** begin refresh with Active P and a deferred C offered (so C is seen); omit P and have its unseen requery return Gone; commit. Assert P retires and C is dropped despite its seen mark; replacement P cannot flush it. Also test failed requery + `refresh_keep` preserves P and does not invalidate C.
6. **QueueFull transaction:** fill the event ring so accepted destroy, exclusion, replacement, and refresh commit return QueueFull. Snapshot Active and Deferred arrays/counters before each attempt and assert the planned descendant mask was not applied; drain, retry, and assert it then applies exactly once. For a replacement whose app-key lookup fails after identity change, assert old P retires and its stale descendants are dropped even though no replacement Announce is emitted.
